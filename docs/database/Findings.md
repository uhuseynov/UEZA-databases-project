# Findings: what we learned about MariaDB's vector search

[← Database](./Home.md) | [Documentation Home](../Home.md)

A summary of what the experiments showed, why the project keeps the vectors in MariaDB, and where that approach loses. Each point links to the page with the measurements: [Vector Search](./Vector-Search.md), [Vector Index State](./Index-State.md) and [FAISS Baseline](./FAISS-Baseline.md).

## What we learned about the vector index

- **Send the query vector as binary.** MariaDB evaluates `VEC_FromText('[0.0123,...]')` again for every row it compares. Written as a hex literal of the vector's binary value, the same search returned the same chunks for all 71 questions, and the full scan went from 608 to 24 ms, filtered searches from 95 to 12.6 ms on average, and the "linked from" filter from 358 to 23 ms. That filter's plan was fine all along; it covers 3,742 chunks, and each paid for parsing the text. ([Vector Search](Vector-Search.md#the-query-vector-text-or-binary))
- **Take the nearest chunks first, then join.** With `articles` joined in the same `SELECT`, the index returned the exact top 10 for every `M`, ignored `mhnsw_ef_search` and took 32 to 67 ms: it searched far more of the graph than the 10 rows needed. With the 10 nearest chunks taken from `article_chunks` alone in a derived table, recall follows `M` and `mhnsw_ef_search`, as for any HNSW index, and the search takes 0.3 ms inside MariaDB. ([Statement shape](Vector-Search.md#statement-shape-join-or-nearest-chunks-first))
- **`M=16`, `mhnsw_ef_search` 40, chosen on the real embeddings.** From `M` 6 to 64, the index recall at `mhnsw_ef_search` 40 rose from 0.87 to 0.99 and the build time from 2 s to 135 s. `M=16` finds the right article as often as the exact search, with 95% of the exact top 10, and builds in 5.5 s; the ingest rebuilds the index after every re-ingest, so build time counts. ([M sweep](Vector-Search.md#choosing-m-and-ef_search))
- **The index cache has to hold the deleted vectors too.** A deleted chunk stays in the HNSW graph until the index is rebuilt. After all chunks were replaced, a search took 72 ms with MariaDB's default 16 MB index cache, 20 ms with 64 MB and 72 ms again at 16 MB: the graph, deleted nodes included, no longer fit, and MariaDB drops the whole cache after a search that leaves it too large. We run MariaDB with 64 MB and rebuild the index after a re-ingest. With the nearest-first statement this mostly stopped mattering: replacing up to half of the chunks changed nothing measurable, and all of them made a search 3 ms slower, even with 16 MB at most 16 ms ([partial replacement](Index-State.md#replacing-part-of-the-chunks)). ([Vector Index State](Index-State.md#cause-1-deleted-vectors-and-the-index-cache))
- **After a rebuild, InnoDB thinks the graph is empty.** `ALTER TABLE ... ADD VECTOR INDEX` leaves the hidden graph table with the statistics of an empty table, and after a restart MariaDB sizes every search by them: index recall stayed around 0.9 for every `M` and `mhnsw_ef_search`. Setting the row count right, and nothing else, gave 0.93 to 1.00; setting it back to 0 lost it again. `make reindex` now inserts and deletes one chunk, which makes InnoDB count the table. This was the cause of the "92 to 94%" in our earlier results. ([Vector Index State](Index-State.md#cause-2-the-graph-tables-statistics-after-a-rebuild))
- **With a filter, the vector index is not used.** MariaDB starts from the filter's index, reads the chunks of the matching articles and sorts them by distance, so filtered searches are exact. Right after a bulk load the statistics were stale and MariaDB scanned every chunk even without a filter; the ingest runs `ANALYZE TABLE` at the end.

## Why MariaDB and not a separate vector store

- **Filters and the vector search are one statement.** With a filter, MariaDB starts from the filter's index and the answer is exact, in 8.4 ms per question. FAISS, which has no metadata, first needed the ids of the allowed chunks from MariaDB (16.6 ms on average), and its HNSW search over them returned 87% of the exact answer. The usual shortcut, "fetch the 10 nearest chunks, then filter", returned fewer than 10 chunks for 16 of the 17 filtered questions ([FAISS Baseline](FAISS-Baseline.md#questions-with-a-filter-17)).
- **Joins with the rest of the data.** "Linked from article X" is a join over the links table. A separate vector store would need the links copied into its metadata and kept in sync.
- **One transaction per article.** The ingest and the sync replace an article's metadata, categories, links, chunks and vectors in one transaction ([src/database/repositories/articles.py](../../src/database/repositories/articles.py)), so there is no second system to update and no window in which the two disagree. FAISS's HNSW index cannot even delete a vector (`remove_ids` is not implemented for it).
- **One system** to run, back up and secure.

## Where this approach loses

- **A separate index searches faster.** FAISS's HNSW search took 0.09 ms in the Python process, MariaDB's 0.46 ms inside the server and 5 ms through the driver. FAISS also built the index 9 times faster (0.6 s against 5.5 s). An application that needs no text and no filters from a database would be faster with FAISS.
- **The index needs looking after.** Deleted vectors stay in the graph until a rebuild, the default cache is small, and a rebuild leaves the graph table's statistics wrong. We work around all three (64 MB cache, rebuilds after large changes, a statistics refresh after the rebuild), but each one first showed up as a puzzling measurement.
- **Small details decide the speed.** Writing the vector as text made searches up to 25 times slower, and the join in the same `SELECT` made the index search most of the graph. Neither is visible in `EXPLAIN`.
- **The query vector is part of the SQL text.** aiomysql cannot send bytes as a parameter with the PyMySQL version we use, so the 3,072 bytes of the vector are written into the statement as a hex literal. It is built from validated floats only, but it is 6 KB of SQL per search.
- **Rebuilds get slow with larger `M`:** 25 s at `M=32` and 135 s at `M=64` for 6,144 chunks.
- **Weak filters scan.** The optimizer chooses the exact plan even when the filter keeps most of the table. At 6,144 chunks that costs at most about as much as a full scan (19 to 24 ms); it grows with the corpus.
- **One vector index per table, tied to one dimension.** Comparing a 384-dimensional model needs a second table.
- **Not measured yet:** concurrent searches, the memory of the index and a larger corpus.
